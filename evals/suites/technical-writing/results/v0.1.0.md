# v0.1.0 evaluation results

Run on 2026-10-10 with the protocol and gates in [`evals/README.md`](../../../README.md). Raw runs (`evals/runs/v0.1.0`, `evals/runs/v0.1.0-rc2`) are git-ignored; this file is the record.

**Verdict: SIMPLIFY in both release candidates, because the gates require both writers to pass and Codex failed.** The owner then released v0.1.0 for Claude Code only, where every gate passed in both candidates.

- **Claude Code:** the skill beats the short rule clearly and consistently. In rc2, judges preferred it in 30 of 42 groups and the rule in 9, on 6 of 7 cases. The mean per-case preference was +0.50, 95% CI +0.31 to +0.69.
- **Codex:** it doesn't. Judges preferred the skill in 15 groups and the rule in 21, on 2 of 7 cases, and both judge families agreed.

Under both writers, the skill had the best deterministic-check and fidelity scores, and no condition leaked a sensitive value. The recommendation is at the end.

### Why C lost cases to B under Codex

C won three Codex cases decisively (runbook +5, PR +4, commit +4) and lost four narrowly (ADR −2, RFC −2, README −1, AI-pattern prose −1). In the README and AI-pattern cases, both judges described B and C as nearly indistinguishable. The ADR and RFC losses had two causes, named by both judge families:

1. **The note to the user repeated the document.** Codex restated the open questions the document already listed, and phrased its own suggestions as requirements the source never set ("resolve X before accepting this ADR"). The Codex judge counted those as invented acceptance gates.
2. **A reason was dropped.** In two of three RFC trials, Codex under C omitted why the limiter fails open. The skill's list of facts that must survive named constraints, numbers, and caveats, but not the reasons given for decisions.

Claude's one losing case (PR description, −4) had the same first cause in a different form: the note cast doubt on a claim that the document stated in the author's voice, so the two read as contradicting each other.

## Changes between the candidates

Three general edits to `SKILL.md`, none referring to a fixture:

- "Keep the facts" rule 2 lists "the reasons given for decisions" among the facts that must survive.
- Rule 4: the agent's suggestions go in the note "offered as suggestions rather than requirements".
- Output: "Point to gaps the document already marks instead of restating them."

The body grew by 38 tokens. rc2 reused rc1's A and B outputs and trigger results: their prompts do not depend on the skill body, and the description was byte-identical. Only C was regenerated, and every group was judged again.

In Pi smoke runs with `--skill`, the release-notes and PR-description queries loaded the skill and the `AGENTS.md` near miss did not.

## Context cost

- Description: 291 characters, about 72 tokens, in every session where the skill is installed.
- Body: about 1,578 tokens, loaded only when the skill activates.
- Measured with Codex, C costs 1,328 more input tokens per call than A in rc1, and B costs 96. Claude Code's per-call usage figure varies by several thousand tokens between calls with the same prompt size (for example 16,349, 8,309, and 20,292 tokens for A, B, and C on one case), so it cannot resolve a difference this small and is not used.

## Disclosures

- **Description fix during rc1.** A Pi smoke test found that the description's unquoted ": " made the frontmatter invalid YAML, which Pi rejected silently. The fix (`4687871`) landed while rc1 was generating. C prompts inject only the body, which did not change, so generations are unaffected; rc1's generation phase recorded the body hash `e810365e1d07` and its trigger phase recorded `a41c52e47b07`, the fixed version.
- **One timed-out generation.** Claude, sensitive runbook, condition A, trial 3 hung for the full 600 s (the other A trials took 107–125 s). It was regenerated, and the CLI reported that cell's model as `claude-opus-5-5[1m]`, the same model with a 1M-token context window. rc2 pins `claude-opus-5-5`.
- **A runner bug found by that timeout.** The judge had graded the group with only B and C, and regenerating A would not have triggered a rejudge. Fixed in `139d981`: such judgements now count as missing and are redone. The group was rejudged with all three outputs before rc1's report.
- **The Codex usage limit stopped rc2 partway.** 19 Codex generations and every Codex judgement failed, and the Claude judge graded 19 Codex groups with only A and B. The run was resumed after the limit reset; the fix in `139d981` redid those 19 judgements with all three outputs. The final rc2 report has no missing or failed results.
- **Gate 3's aggregation** was tightened after the adversarial review and before any full run: one verdict per judged group instead of one per dimension, plus the per-case condition.
- **Iterating on the same cases.** rc2 follows a failed gate on the same seven cases that motivated the edits. Both runs are reported in full. The edits are general rules, but rc2 alone cannot show they generalize; a held-out set written by other people can.

## Limitations

- Seven cases, all written by the skill's author, and no held-out set.
- Model judges, checked by one person on five Claude-writer groups.
- Condition C injects the body rather than loading the skill through each harness, so these numbers measure the content. Loading is measured separately by the trigger runs.
- One writer model per family, each at one effort level.

## Recommendation

Against the success criterion (the skill must beat a short writing rule enough to justify its cost), the answer depends on the writer:

- **Claude Code: use the skill.** It beat the short rule in both candidates and with both judges, for about 1.6k tokens per activation and 72 always-loaded tokens.
- **Codex: use the short rule instead.** The skill raised fidelity there (83% vs 76% judge fidelity, 98% vs 95% of checks), but judges preferred the short rule's output, mainly because Codex under the skill repeats itself. The rule belongs in the global instructions Codex reads.
- **Pi: unmeasured for quality.** It runs the same OpenAI model family as Codex, so treat it like Codex until measured.

A third round on these seven cases was ruled out before rc2 ran: more edits tuned on the same fixtures would fit them. If Codex support is worth pursuing, the next step is held-out cases written from real documents by other people. A rule aimed at repetition, such as "state each fact once", is a hypothesis to test there.
