# v0.3.0 evaluation results

Run on 2026-10-20 at `b5c8209` with the protocol and gates in [`evals/README.md`](../README.md), for the Claude Code writer only. The raw run (`evals/runs/v0.3.0`) is git-ignored; this file is the record.

**Verdict: SHIP for Claude Code.** Every gate passed. The Codex writer was not rerun; see Disclosures.

- Judges preferred the skill over the short rule in 46 of 54 groups and the rule in 4, on all 9 cases. The mean per-case preference was +0.78, 95% CI +0.61 to +0.93, against +0.88 in v0.2.0.
- Under the skill, outputs averaged 298 words, against 494 under the short rule and 318 for the skill in v0.2.0. The skill stayed within its length cap in 18 of 27 generations, against 11 of 24 in v0.2.0.

## Length caps and paragraph limits

Each length cap is 1.5 times the case's reference solution, relative to the input, and was fixed before any run of the changed skill. C was over its cap in every trial on three cases:

| Case | C, mean ratio to input | Cap |
|---|---|---|
| Runbook | 1.78 | 1.6 |
| Review comments | 0.68 | 0.6 |
| Bug issue | 0.86 | 0.7 |

The commit message and the PR description, over their caps in every v0.2.0 trial, stayed within them in every trial.

C broke a paragraph limit in 3 of 27 generations: the bug issue in 2 of 3 trials and the review comments in 1. A and B broke it in every trial of the commit message, review comments, and bug issue.

## Triggering

Recall was 90% on should-trigger queries and the false-positive rate 0% on near misses, over 60 runs. The misses are the same queries as in v0.1.0 and v0.2.0: q7, the support-team explainer (1 of 3), and q10, the handoff doc for a named colleague (2 of 3). The description did not change, and no query asks for an issue.

## Judge spot-check

The repository owner decided the five groups in the blind packet from `run.py calibrate` (Claude writer, one random trial per case) before seeing the key.

| Case, trial | Owner's call | Claude judge | Codex judge |
|---|---|---|---|
| RFC, t1 | skill | tie | skill (agree) |
| Review comments, t1 | skill | skill (agree) | skill (agree) |
| README, t1 | skill | short rule | skill (agree) |
| PR description, t3 | skill | skill (agree) | skill (agree) |
| Bug issue, t2 | skill | skill (agree) | skill (agree) |

Agreement: 5 of 5 with the Codex judge and 3 of 5 with the Claude judge, 8 of 10 verdicts overall, as in v0.2.0. The RFC tie was a 2-to-2 split of the dimensions: the skill won naturalness and brevity, and the short rule won clarity, with its decisions in one table, and conventions.

On the README, the Claude judge preferred the response the owner ranked worse, which v0.2.0 did not see. It ranked the skill's output best on naturalness but worse on clarity, brevity, and conventions, noting that it renamed the top heading without saying so, which breaks existing links. The owner gave one reason for all five calls, tidier and briefer output, so the two disagree on brevity in this group.

Five groups are enough to rule out a badly miscalibrated judge, not to measure small biases, and they cover the Claude writer only.

## Disclosures

- **Codex writer not rerun.** At the owner's choice, to stay within the Codex plan's usage limits, this run measured the Claude Code writer only. Codex still judged every group. v0.1.0 found that the short rule did as well as the skill with Codex, and that recommendation is not re-measured here.
- **Recovered release.** The release pull request (#7) was merged before this file existed, so the release workflow tagged nothing. This file was committed afterwards and v0.3.0 tagged by hand, as README.md, "Versioning", describes.
- **Revisions after smoke runs.** In #6, the review-comment note gained "three sentences" after one smoke round, and the issue note was revised twice, ending with a 150-word budget. Those revisions were tested on the `review-comments` and `bug-issue` fixtures, so both cases carry a fitting risk.
- **Paragraph limits restate the skill.** The limits come from the skill's own rule, not from the references, so they measure compliance with it. B and A were never told about them.
- **Grader fixed before this run.** The paragraph check first skipped every fenced block, so a document wrapped in a markdown fence passed unread. #6 fixed it.
- **Unpinned judge model.** The Codex judge used the CLI's default model, which the runner does not record.
