# v0.4.0 evaluation results

Run on 2026-10-21 with the protocol and gates in [`evals/README.md`](../README.md), for the Claude Code writer only. This is the run PR #9 was evaluated with, reused at the owner's choice instead of a fresh release run; see Disclosures. The raw run (`evals/runs/v0.4.0`) is git-ignored; this file is the record.

**Verdict: SHIP for Claude Code.** Every gate passed. The Codex writer was not run.

- Judges preferred the skill over the short rule in 68 of 78 groups and the rule in 5, on 12 of 13 cases. The mean per-case preference was +0.81, 95% CI +0.63 to +0.94, against +0.78 on 9 cases in v0.3.0.
- Under the skill, outputs averaged 446 words, against 642 under the short rule. On the 9 cases v0.3.0 also had, they averaged 308 words, against 298 under the v0.3.0 skill.

Agreement: 5 of 5 with the Codex judge and 4 of 5 with the Claude judge, 9 of 10 verdicts overall, against 8 of 10 in v0.2.0 and v0.3.0.

On the README, as in v0.3.0, the Claude judge preferred the response the owner ranked worse. It ranked the skill's output best on naturalness, tied on brevity, and last of three on clarity and conventions, for two defects that are in the output: it wraps the README in a three-backtick `markdown` fence around three-backtick code blocks, which breaks when rendered, and it renames the top heading "Getting Started With logship" to "Getting started", which breaks links to it. The rename follows the skill's rule for sentence-case headings, and v0.3.0's spot-check found the same one. The README is also the one case where the judges, over all six groups, preferred neither the skill nor the short rule.

Five groups are enough to rule out a badly miscalibrated judge, not to measure small biases, and they cover the Claude writer only.

## Disclosures

- **Reused development run.** At the owner's choice, this is PR #9's final run, copied from `evals/runs/sel-new`. Its skill, `cases.json`, and short-rule hashes match the release (`9c7635f47c0a`, `cf382fb38e57`, `98a0dd229ec0`). The skill's text was fixed before the run, and nothing changed after it. Its A and B outputs for the 9 earlier cases, and its trigger runs, come from the v0.3.0 run; the A and B outputs for the 4 new cases come from PR #9's baseline run.
- **Codex writer not run.** As in v0.2.0 and v0.3.0, to stay within the Codex plan's usage limits. Codex judged every group.
- **Revisions after smoke runs.** In PR #9, the skill went through two revision rounds after one-trial smoke runs. In the same PR, after smoke runs, three new fixtures were corrected for technical errors, the drop checks were narrowed so a note naming removed content passes, the PR-compression prompt was changed to say reviewers find the description too long, and `pr-from-branch` was added. The skill's example of a fact stated twice, a test gap that is also a risk, was written after seeing one case's output, so that case carries a fitting risk.
- **Drop checks restate the references.** Each new case's drop checks encode its reference's choice of what belongs elsewhere, such as an ADR's implementation plan. B and A were never told about them.
- **Spot-check draw.** The calibration packet picks five cases at random; none of the four new cases was drawn.
- **Unpinned judge model.** The Codex judge used the CLI's default model, which the runner does not record.
